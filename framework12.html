A clear hierarchy for consistent, accessible and flexible content

The framework provides the visual language and building blocks. The CMS uses this structure to assemble pages with consistent rules, while AI can use the same information to create and validate content.

1. Page and section structure

Defines the overall layout, content boundaries and full-width sections.

  • Page containers and maximum content width
  • Full-width and full-bleed sections
  • Page gutters and section spacing
  • Responsive behaviour at the page level

Paragraph text uses a shared readable measure targeting approximately 75 characters per line, separate from container width. Wider containers support layouts and collections without requiring wide paragraphs.

The framework determines gutters, widths and responsive behaviour rather than exposing arbitrary values to editors.

2. Groups and layout patterns

Groups associate related components and can share approved presentation. Layout patterns arrange components; the framework controls spacing, alignment rules, column widths and responsive stacking.

  • Shared background, padding and width
  • Consistent spacing between child components
  • Framework-defined borders and edge treatments
  • Behaves predictably when nested

Layout patterns

Retain a two-column pattern for two related pieces of content. The framework controls column sizing, spacing and stacking.

Link, Document and Course lists should share automatic one- or two-column layout rules based on available width and item count, with no editor layout controls.

4. Approved presentation settings

Editors choose a component, add content and apply approved presentation settings where appropriate. These do not expose arbitrary framework values.

  • Approved surfaces: Default, Light and Dark
  • Supported presentation patterns, such as Navigation lists or cards
  • Framework-defined typography, iconography and edge treatments
  • No individual editor controls for spacing, radius, widths or responsive arrangements

5. Framework tokens and utilities

Provide consistent spacing, sizing, colours and responsive behaviour.

  • Spacing (section, component, content)
  • Sizing and width constraints
  • Grid and flex layout
  • Colour palette and surface tokens
  • Responsive and container queries
  • Accessibility helpers

Proposed framework defaults

  • Use rounded edges throughout components; keep full-width containers square. Remove the square/rounded editor choice.
  • Manage component radius through a shared responsive token. Nested treatments and pill-shaped controls use related tokens.
  • Standardise surfaces to Default, Light and Dark. Remove Medium from future editor options.
  • Apply a shared paragraph measure of approximately 75 characters.
  • Control spacing, alignment and responsive layouts through the framework.

Clear purposes, structured content requirements and predictable rules should support future AI-assisted recommendations and assembly, with editors reviewing the results.

6. Content sources and integrations

Components can display manually entered, CMS-selected or externally retrieved content. Sources supply data; components determine presentation and behaviour.

Equivalent content should use consistent styles and responsive behaviour regardless of source, including the CMS, Pure and Salesforce. For example, research groups retrieved from Pure should receive the same treatment as an equivalent CMS article list.

Navigation and related content

Navigation supports List, Cards and Cards with images. Each instance uses one selection method: manually curated links (including CMS articles and external URLs), or dynamic retrieval using tags, filters or an approved source.

Support related content through Navigation with an appropriate heading. Dynamic tag-based content is a confirmed need; a separate Related content component is not proposed.

Area to explore: technical source configuration, external retrieval and data management.
